## Current release decision (supersedes the historical status table below)

**HOLD — application changes and the two unpublished migration revisions are implemented, but the release is not deployable until those revisions are manually reviewed and applied, credentials are rotated, and same-commit deployment acceptance is complete.** No code was pushed, no deployment was triggered, the migrations were not executed or tested by the agent, and the production database was never accessed. The ordered chain is `20260909_add_manuscript_import_jobs_and_latency_indexes.py` followed by `20260909_add_book_data_generations.py`; the generation schema/backfill checklist is in `docs/generation-migration-spec.md`.

Four release prerequisites remain outside this agent's permitted or verified scope:

1. **Credential rotation.** A local Compose diagnostic expanded the existing secret-bearing backend environment into an audit-tool transcript. No values are repeated in this report and the environment file was not edited, but every credential present in that output must be treated as exposed, rotated at its provider, and replaced by the owner before release. At minimum review OpenAI, Paddle, Supabase, R2/AWS, Redis/JWT, Docker Hub, Resend, and Sentry credentials.
2. **Schema hardening.** ORM metadata now declares generation-aware identities for chunks, summaries, characters, aliases, voice profiles, and duplicate suggestions, plus the stable reading-progress identity. Existing production data must still be checked and backfilled before adding those constraints and indexes. Chapter `(book_id, number)` cannot be made globally unique yet because ingestion and legacy-repair paths temporarily preserve duplicate source numbers; it needs a canonical-generation design rather than a naïve constraint. Repository policy permits creating and revising unpublished migrations, while published/shared/applied revisions remain immutable; no migration was executed for this audit.
3. **Manual migration and rollout.** Full-book rebuild now stages derived rows behind a generation boundary and atomically promotes only a complete generation; failures retain the prior active data. The first revision creates the durable `manuscript_import_jobs` table with UUID keys, JSONB payloads, lifecycle validation, and its query indexes, then adds the latency indexes. The following revision adds the compatible generation table, columns, identities, and backfill. Both have been statically reviewed as one linear chain, but must still be reviewed and executed manually on staging and production before this backend can start.
4. **Cross-host release coupling and production-topology acceptance.** Read-only production probes confirmed that `getlorevia.com` redirects to a Vercel-hosted `www.getlorevia.com`, while `api.getlorevia.com` is served through Cloudflare to the VPS. Both `/health` and `/ready` return 200, and Vercel's same-origin `/api/v1` rewrite reaches the protected API. The deterministic public-boundary check on 2026-09-08 also passed readiness, anonymous auth denial, CORS, redirects, and security headers, but correctly failed because the currently deployed frontend returns 404 for the candidate's `/api/release` endpoint and the deployed API health/readiness responses do not yet carry the candidate's no-store policy. The repository implements both controls, but this audited candidate is intentionally unpushed; the Vercel production-branch setting, actual same-commit promotion, and rollback owner remain external state. A latest-image, local Compose-network acceptance run passed real registration/verification cookies, CSRF and hostile-origin rejection, Redis-backed refresh rotation/replay rejection, PostgreSQL project creation, cross-tenant denial, and logout invalidation. Staging/VPS must still verify the real proxy chain plus upload compensation, signed Paddle replay, Redis disruption, and Celery redelivery under the production topology.

These are release blockers because exposed credentials can be replayed, the new generation-aware code cannot run before its schema exists, unenforced identities can permit duplicate rows, and frontend/backend version skew can break release behavior. They should not be bypassed merely because the automated source gates pass.

The “representative full allocation” below assumes chat usage is 80% uncached input and 20% output, or about `$0.24` per one million total tokens. Actual provider billing is usage-based: an inactive user costs `$0`, cached input and embeddings are cheaper, and output-heavy work is more expensive. The estimates exclude VPS, database, storage, email, monitoring, and payment fees.

## Executive assessment

LoreVia has a sound service-oriented application structure, explicit book-scoped authorization helpers, durable task-control models, signed Paddle webhooks, bounded upload parsing, structured logs, and a realistic VPS deployment topology. It was functional, but not ready to be treated as a strong multi-user production boundary: browser state could cross account boundaries on a shared profile, Supabase OAuth could link an account without explicit email confirmation, capability URLs could enter access logs, and several asynchronous workflows could duplicate work or preserve partial state.

The application-side full-book replacement and durable upload-intent work is implemented. The unpublished latency-index and generation/backfill revisions are present as one linear chain and statically reviewed, but production still requires the manual review and execution described in `docs/generation-migration-spec.md`. No published/shared/applied migration was edited and no migration was executed or tested by the agent.

## 1. Current architecture

The concise component and data-flow map is in [ARCHITECTURE.md](ARCHITECTURE.md). In summary:

- Next.js 15 and React 19 provide the browser application. Axios calls the same-origin `/api/v1` surface; TanStack Query owns server state and Zustand owns authentication and preferences.
- FastAPI runs under Gunicorn/Uvicorn. Routes delegate workflows to `services/` and reusable domain logic to `utils/`.
- PostgreSQL is the source of truth. pgvector stores book and character embeddings. Redis provides Celery transport, session/security state, rate limiting, leases, and derived caches.
- Dedicated Celery queues handle extraction, analysis, embeddings, intelligence, and scheduled maintenance.
- Cloudflare R2/S3-compatible storage holds uploads and generated assets. Paddle owns subscription billing; Supabase provides OAuth identity; OpenAI is the primary model provider with a configured Gemini fallback.
- Nginx, the API, Redis, workers, and Beat are represented in the VPS Compose stack. The tracked production topology does not fully represent frontend hosting.

## 5. Security assumptions

1. `JWT_SECRET`, Paddle webhook secrets, Supabase credentials, R2 credentials, and database credentials are high-entropy, unique per environment, stored outside the repository, and rotated on exposure.
2. Production runs with `DEBUG=false`, HTTPS at the first trusted edge, secure cookies, a correct public application origin, and no localhost CORS origin.
3. The backend port is not internet-accessible around Nginx; only the trusted edge can supply verified forwarding headers.
4. PostgreSQL and Redis are private-network services. Redis persistence, memory policy, authentication/network ACLs, and backups match the state stored there.
5. R2 buckets are private by default; all private access is authorized server-side or uses short-lived, scoped capabilities.
6. Every child object is authorized through its owning book/user. UUID unpredictability is not an access control.
7. Manuscript text, retrieved RAG context, user prompts, filenames, model output, and webhook JSON are untrusted input.
8. Database backups are encrypted, access-audited, retention-limited, and never attached as ordinary CI artifacts.
9. Paddle is authoritative for billing, but local application of provider events must remain signature-verified, idempotent, and order-aware.
10. Late-acknowledged Celery tasks can execute more than once; replay safety is mandatory.

## 6. Scaling bottlenecks

- Intelligence remains single-concurrency, but scheduled maintenance now has a separate queue and worker; interactive intelligence capacity should still be monitored as usage grows.
- Full-book replacement extraction/analysis now uses atomic generation promotion; production must apply the required schema/backfill before that runtime can start.
- Object-storage and database writes remain separate systems, but durable pre-upload intents plus hourly reconciliation now recover hard-process-death orphans after a 24-hour grace period.
- PostgreSQL carries transactional, full-text/domain, and vector retrieval load without documented production query plans or pool saturation metrics.
- Redis is simultaneously broker, cache, limiter, and security/session dependency, expanding its failure blast radius.
- Large manuscripts amplify per-chapter queries, serialized payloads, prompt construction, embedding volume, and LLM spend.
- Frontend deployment is not versioned in the same tracked release topology as the API.
- Browser telemetry is consent-gated and metadata-only by design; production alerting and request-ID support workflows still need an external owner.
